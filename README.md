# AgriProvider
React Native/Expo SDK 58 for Android, iPhone and web, with a Fastify/TypeScript API and PostgreSQL/Prisma.

## Project layout
- apps/mobile: the active Expo application, with dedicated provider, assessor, QA and admin routes.
- apps/api: the active API, migrations, workers, CLI and functional tests.
- packages/shared: shared validation, roles, permissions and South African ID checks.
- app and backend: original prototype source, preserved rather than deleted.
- docs: architecture, decisions, deployment and testing notes.

Run commands from this directory. Do not launch the old app/app or backend folders.

## Local setup
Node 22+, pnpm 11.25.0 and PostgreSQL 18 are used. Install with pnpm install, then copy each .env.example to .env and supply locally generated secrets. No real credentials belong in Git.

The development database is isolated on 127.0.0.1:55432, with databases agriprovider and agriprovider_test. It does not modify the pre-existing Windows PostgreSQL service. Its data is in .data/postgres. It binds only to loopback and uses trust authentication for this local-only development cluster.

Commands:
- pnpm db:generate
- pnpm db:migrate
- pnpm seed
- pnpm dev:api
- pnpm dev:web
- pnpm dev:mobile
- pnpm build:web
- node scripts/serve-web.mjs (serves the production web export on port 4173)
- pnpm typecheck
- pnpm lint
- pnpm test
- pnpm exec playwright test

On this Windows computer, scripts/start-local.ps1 starts the database, API and Expo servers with logs in .data/logs. scripts/stop-local.ps1 stops only processes recorded by that launcher.

Web development runs on http://localhost:8082. The API is http://localhost:4000. Expo runs on port 8081. Android and iPhone must share the computer's Wi-Fi network; use the exp:// address printed by Expo. For LAN browser access, include that exact web origin in CORS_ORIGINS. The API address is derived from Expo's host unless EXPO_PUBLIC_API_URL overrides it.

## Invitations and forgotten passwords
There is no public sign-up. Admin invites role-scoped accounts. Setup/reset links are single-use and expire. In local development, the outbox writes email JSON files to .data/mail. Open the newest matching message and copy its link. These files contain sensitive development setup/reset links and are ignored by Git. With SMTP configured, the same flow sends real email.

Bootstrap a fresh non-demo database using:
pnpm --filter @agri/api bootstrap:admin --email administrator@example.org --name "Administrator Name"

The worker delivers the setup link. Bootstrap refuses when an admin already exists unless ALLOW_BOOTSTRAP=true and --force are both supplied.

## Golden journey
1. Admin creates an accredited provider, programme, cohort with scheduled sessions, users and assessor assignments.
2. Provider registers learners with valid IDs, phone numbers and consent; full cohorts reject further enrolment.
3. Provider records every learner's attendance. Offline entries remain account-scoped and sync idempotently.
4. An assigned assessor submits a complete Pass/Fail batch. This automatically attaches the assessor report.
5. Provider uploads the five provider-owned evidence types, including signed certificates for learners who passed.
6. A different assessor verifies the checklist and signs off. The grading assessor cannot self-moderate.
7. Provider submits the pack; QA verifies all three conditions, resolves follow-up findings and unlocks.
8. Unlock records a certification/outbox event. It changes a status only; no real money moves.

## Security and privacy
Validation runs on the server and client. SA IDs must be exactly 13 digits and pass date, citizenship and Luhn checks. IDs and phones are encrypted at rest; lists expose masked IDs. Roles and provider scope are immutable, and a database trigger protects audit rows against updates/deletes. Passwords use Argon2id. Sessions use short-lived opaque access tokens and rotating refresh tokens with reuse detection. Web refresh tokens are HTTP-only cookies; native refresh tokens use SecureStore. Login has rate limits and lockout. Admin MFA is mandatory.

Role permissions:
| Role | Permitted work |
|---|---|
| Provider | Its own cohort enrolment, attendance and evidence |
| Assessor | Assigned cohort grading, independent moderation and schedule |
| QA | Audits, findings, condition verification, reject/unlock, suspension recommendations |
| Admin | Configuration, invitations, access control, governance and operational metadata |

With two or more active admins, sensitive actions require another admin's approval. The last active admin cannot be deactivated, and an admin cannot act on their own account through administrative controls.

## Offline behaviour
Native uses a separate SQLite database per user. Web uses separate IndexedDB databases. Logout locks the user's store and clears the active identity; another account cannot see or send that queue. Attendance, registration and evidence uploads are queued with client operation IDs. Grading can be queued. Files are copied into app-owned native storage before queuing.

Reconnect, foreground and manual sync are supported. Native background sync is best-effort and OS-scheduled; it needs a development/production build. Web background execution is not guaranteed. The exported web app precaches its shell and route assets; development Metro servers do not provide a production offline guarantee. Browser storage can be cleared by the user/browser. Server validation is authoritative if capacity, assignments or milestone status changed while offline. Conflicting items remain visible for review.

## Mobile builds and notifications
eas.json contains development, preview and production profiles. Supply your Expo project ID and app signing configuration before EAS builds. Android preview uses an APK; iPhone installation requires the appropriate Expo/Apple distribution setup. No signed store binaries or physical-device test results are implied by Metro bundle success.

In-app notifications work locally. Push is opt-in from Account and requires a configured Expo project, device credentials and a development/production build. Camera evidence capture asks for device permission and compresses photos. Native permissions and background scheduling must also be checked on the user's phones.

## Production
See docs/deployment.md and render.yaml. Production requires Neon, SMTP, private S3/R2 storage, a configured virus scanner, HTTPS domains and real integration endpoints. The API refuses production boot without required service configuration. This repository does not claim a live deployment.
