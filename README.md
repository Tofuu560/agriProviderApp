# AgriProvider
React Native/Expo SDK 58 for Android, iPhone and web, with a Fastify/TypeScript API and PostgreSQL/Prisma.

## Project layout
- apps/mobile: the active Expo application, with dedicated provider, assessor, QA, admin and learner routes.
- apps/api: the active API, migrations, workers, CLI and functional tests.
- packages/shared: shared validation, roles, permissions and South African ID checks.
- app and backend: original prototype source, preserved rather than deleted.
- docs: architecture, decisions, deployment and testing notes.

Run commands from this directory. Do not launch the old app/app or backend folders.

## Local setup
Node 22+, pnpm 11.25.0 and PostgreSQL 18 are used. Install with pnpm install, then copy each .env.example to .env and supply locally generated secrets. No real credentials belong in Git.

The working development API uses Neon PostgreSQL in Frankfurt on branch `my-new-app`; see [deployment details](docs/deployment.md). The original local database and isolated test databases remain on 127.0.0.1:55432. Their data is in .data/postgres; this loopback-only development cluster uses local trust authentication and does not modify the pre-existing Windows PostgreSQL service. Do not seed or reset the working Neon database.

## Account requests, learner access and MFA
Providers, assessors and QA officers can use **Create account**. A new request has `status=PENDING` and `approvalStatus=PENDING`; it receives no access or refresh token. Signing in with correct credentials shows **Awaiting Administrator Approval**. Only Admin can approve or reject a request from **Dashboard > Review pending accounts**. Provider approval requires verified accreditation dates. An assessor starts with no assignments until Admin assigns cohorts. Rejection requires a reason and is audited.

Administrators cannot self-register. Bootstrap or an existing administrator invites them. Admin invitation acceptance displays a locally generated authenticator QR code. An active admin who has not configured MFA receives a ten-minute, single-use MFA setup challenge at login, with no workspace session until the code is verified. Recovery codes are shown once after this login setup. Existing MFA users enter a current authenticator or recovery code; their setup key is never re-displayed on login.

Learners cannot self-register. A provider first registers a learner, then chooses **Create portal access** in Learners. Enter a unique email, location, matching phone number and initial password. The learner receives a single-use password setup link, and the provider receives an account-creation confirmation. Passwords are not emailed. This online-only action does not put credentials in the offline queue. Learners see only their own courses, provider-published materials, lesson schedule, attendance, outcomes and QA-verified certification records. Shared cohort evidence bundles are never exposed to learners. Certificate views are verification records, not downloadable copies of the cohort's signed evidence pack.

Providers use **Manage programmes** to create programmes, add cohorts, close/reopen their own cohorts, schedule modules and publish materials. Admin has a read-only cohort overview. Date fields open calendar controls; all entered and displayed times use SAST (UTC+02:00), independently of device time zone. Staff signup, invitations and learner account creation offer South African provinces; Other country reveals country-specific province/state choices and validates the phone number against that country.

Administrator-issued invitations remain available as an alternative for pre-approved accounts. Setup/reset links are single-use and expire. Pending public requests cannot bypass approval through these links or generic account actions. In local development, the outbox writes email JSON files to .data/mail. Open the newest matching message and copy its link. These files contain sensitive development setup/reset links and are ignored by Git. With SMTP configured, the same flow sends real email.

Bootstrap a fresh non-demo database using:
pnpm --filter @agri/api bootstrap:admin --email administrator@example.org --name "Administrator Name"

The worker delivers the setup link. Bootstrap refuses when an admin already exists unless ALLOW_BOOTSTRAP=true and --force are both supplied.

## Golden journey
1. Admin approves staff/provider access and assigns assessors. The provider creates the programme, cohort and lesson schedule.
2. Provider registers learners and creates their portal accounts. Learners use **Documents** to upload their own ID, consent and supporting files; providers see those files in that learner's pack.
3. Provider records attendance. In **Learners**, choose **Evidence pack for [name]**; add enrolment, attendance and other documents for that learner. **Evidence** also has a learner selector.
4. Choose **Submit this learner to assessor**. Each learner has an independent review state. Assigned assessors see those packs in Grade Learners and Moderation.
5. Assessor submits results; the API creates a separate assessment report per learner. The provider adds signed certificate evidence for passing learners and resubmits if documents changed.
6. Assessor chooses **Approve and send this learner to QA**. QA verifies each learner pack individually. When all learners reach QA, the overall milestone becomes ready for review. Independent moderation sign-off remains required for final certification.
7. QA verifies the cohort's enrolment, attendance and certification conditions, resolves findings and unlocks the milestone. No real money moves.
8. **Reject / Request Re-upload** requires only a nonblank message and can reopen an already verified/unlocked record. With no cohort files selected, the message applies to the whole pack. Corrections invalidate the current certification view; old files and the audit trail remain.

### Upload history and testing certificates
Every upload creates a new evidence record and storage object. Repeated synchronization of the same operation does not duplicate it. Earlier files remain available in history; validation uses the latest file for each learner/document type, with legacy cohort documents retained for compatibility. Learners can download only individually scoped documents belonging to themselves.

In development and test environments, **certificate** uploads accept any file type (including synthetic text files). Size limits, malware checks, passing results and signature declarations still apply. Other evidence accepts PDF/JPG/PNG. Production retains the stricter certificate file-type checks.

### Account email delivery
New staff applications receive an acknowledgement and an approval/rejection email. Administrator invitations and provider-created learner accounts send a setup email to the new address and a confirmation to the creator. Emails use the durable encrypted outbox with retries. Learner setup links currently expire after one hour; use Forgot password to request a fresh link.

With `MAIL_MODE=local`, delivery produces JSON messages in `.data/mail`; it does not send to an internet inbox. For real inbox delivery configure `MAIL_MODE=smtp`, `SMTP_URL`, `MAIL_FROM` and the reachable `APP_URL`, and run the worker or set `INLINE_WORKER=true`. Do not commit credentials or generated mail.

## Security and privacy
Validation runs on the server and client. SA IDs must be exactly 13 digits and pass date, citizenship and Luhn checks. IDs and phones are encrypted at rest; lists expose masked IDs. Roles and provider scope are immutable, and a database trigger protects audit rows against updates/deletes. Passwords use Argon2id. Sessions use short-lived opaque access tokens and rotating refresh tokens with reuse detection. Web refresh tokens are HTTP-only cookies; native refresh tokens use SecureStore. Login has rate limits and lockout. Admin MFA is mandatory.

Role permissions:
| Role | Permitted work |
|---|---|
| Provider | Its own cohort enrolment, attendance and evidence |
| Assessor | Assigned cohort grading, independent moderation and schedule |
| QA | Audits, findings, condition verification, reject/unlock, suspension recommendations |
| Admin | Configuration, account approval, invitations, access control, governance and operational metadata |
| Learner | Their own course materials, lessons, attendance, results, certification records and private document uploads |

With two or more active admins, sensitive actions require another admin's approval. The last active admin cannot be deactivated, and an admin cannot act on their own account through administrative controls.

## Offline behaviour
Native uses a separate SQLite database per user. Web uses separate IndexedDB databases. Logout locks the user's store and clears the active identity; another account cannot see or send that queue. Attendance, registration and evidence uploads are queued with client operation IDs. Grading can be queued. Files are copied into app-owned native storage before queuing.

Reconnect, foreground and manual sync are supported. Native background sync is best-effort and OS-scheduled; it needs a development/production build. Web background execution is not guaranteed. The exported web app precaches its shell and route assets; development Metro servers do not provide a production offline guarantee. Browser storage can be cleared by the user/browser. Server validation is authoritative if capacity, assignments or milestone status changed while offline. Conflicting items remain visible for review.

## Mobile builds and notifications
eas.json contains development, preview and production profiles. Supply your Expo project ID and app signing configuration before EAS builds. Android preview uses an APK; iPhone installation requires the appropriate Expo/Apple distribution setup. No signed store binaries or physical-device test results are implied by Metro bundle success.

In-app notifications work locally. Push is opt-in from Account and requires a configured Expo project, device credentials and a development/production build. Camera evidence capture asks for device permission and compresses photos. Native permissions and background scheduling must also be checked on the user's phones.

## Production
See docs/deployment.md and render.yaml. Production requires Neon, SMTP, private S3/R2 storage, a configured virus scanner, HTTPS domains and real integration endpoints. The API refuses production boot without required service configuration. This repository does not claim a live deployment.
